# 下一步预览能力规划

> 前置：[architecture.md](./architecture.md)（`PreviewModule` 契约与体积预算）、
> [media-preview.plan.md](./media-preview.plan.md)（媒体车道，已落地）。
> 基线 `dsh-v0.2.0-rc.2` / 桌面版 `0.2.1-rc.1`。状态：规划稿。

## 1. 先看空白在哪（按实际后缀盘点）

内置渲染器已经认领的后缀：

| 类别 | 后缀 | 渲染器 |
|---|---|---|
| 纯文本兜底 | 全部 | `text` |
| 代码高亮 | **json, yaml, yml, toml, ini, xml**, 常见语言 | `code` |
| 表格 | xlsx, xls, **csv, tsv** | `excel` |
| 文档 | doc, docx, ppt, pptx | `office`（Host 侧 LibreOffice） |
| 其他 | pdf, md, html, png/jpg/… | 各自 |

**没有任何渲染器认领、目前只能当纯文本看**的后缀：

```
jsonl  ndjson  log  diff  patch  ipynb  zip  ttf  otf  woff2  glb  gltf
```

这就是真正值得做的空白——不是"再造一个 JSON 查看器"，而是这些**结构明确却只能读到源码**的格式。

## 2. 新增格式的准入规则（沿用媒体那一轮的教训）

1. **数据通路优先走 RPC**：能用 `text-pages` 或 `bytes-complete` 解决的，**不要开 HTTP 旁路**。
   桌面版代理会剥 `Content-Length`，任何依赖响应头的设计在桌面版都会降级。
2. **不得依赖响应头语义**：不许依赖 `Content-Encoding`、`Content-Length`、ETag。
3. **体积预算**：单个格式 ≤ 8 KB gz；需要 > 30 KB gz 解析库的，单独评审。
4. **无重复认领**：同一后缀只能出现在一个模块里；`previews/index.ts` 是唯一清单。
5. **失败可降级**：解析失败必须回退成纯文本视图，而不是空白或报错页。

## 3. 分批建议

### P2 — 零依赖、高价值（建议下一批）

| 格式 | 价值 | 数据通路 | 成本 | 风险 |
|---|---|---|---|---|
| **diff / patch** | 编码 agent 的输出里极常见；统一 diff 渲染比源码可读性高一个量级 | `text-pages` | 低（约 150 行：hunk 解析 + 行着色 + 折叠） | 无 |
| **log** | 日志是最常被打开的大文件；需要尾部跟随、级别着色、关键词过滤 | `text-pages`（天然增量，大文件免疫代理） | 中（复用 `text-pipeline` 与分页） | 过滤性能（用行索引，不做全文扫描） |
| **jsonl / ndjson** | 事件流、agent trace、导出数据；一行一对象，天然可增量 | `text-pages` | 低（逐行 `JSON.parse` + 表格/展开两种视图） | 单行超大对象要截断显示 |

这三个都不引入依赖，且都能复用现有内核（分页、行索引、错误边界）。

**状态：P2 全部完成（diff / log / jsonl），CSV 虚拟滚动同步落地。**

### P3 — 需要先做一个决定

| 格式 | 价值 | 要决定什么 |
|---|---|---|
| **json**（树视图） | 大 JSON 折叠浏览远好于源码 | 内置 `code` 已认领 `json`，我们是**压过它**还是让位？建议：压过，但必须同时提供「源码」视图，并在标题里写清楚 |
| **yaml** | 配置文件高频 | 需要解析器。手写子集（锚点、多文档、流式语法）风险高；引 `js-yaml` 约 20–40 KB gz，接近预算上限 → **建议推迟**，先只做「大纲」（顶层键 + 缩进折叠），不做语义解析 |
| **ipynb** | 笔记本阅读 | 复用 JSON 解析 + 代码块渲染；成本中等，价值中等 |

### P4 — 只有明确需求才做

| 格式 | 障碍 |
|---|---|
| **zip** | 需读中央目录（可用 RPC 按 offset 读，不受代理影响），但解压要靠 `fflate`（约 10 KB gz）→ 可接受，优先级取决于是否真的要在侧边栏看压缩包 |
| **字体 ttf/otf/woff2** | 需字形渲染，价值窄 |
| **glb/gltf** | 依赖 3D 运行时，体积远超预算 |

## 4. 与既有待办的顺序关系

当前积累的待办（来自 architecture.md 的分期）：

```
P3（旧）CSV 虚拟滚动 + 行索引 + 跳转   ← 和「log」共用同一套内核，建议合并做
P2（新）diff / log / jsonl
P3（新）json 树 / ipynb
P4（新）zip / 字体
```

**建议把 CSV 虚拟滚动提到 P2 一并做**：它和 log 的"行索引 + 窗口化"是同一件事，做一次两头受益；否则 log 会重复实现一遍分页。

## 5. 每个格式的验收标准

| 格式 | 验收 |
|---|---|
| diff / patch | 1000 个 hunk 的补丁滚动流畅；`+/-/@@` 着色正确；无法解析时自动回退纯文本 |
| log | 50 MB 日志可打开，内存增长 ≤ 30 MB；级别过滤即时生效；尾部跟随可关闭 |
| jsonl | 10 万行可流式浏览；坏行单独标出且不影响其它行 |
| json 树 | 10 MB JSON 可展开/折叠；源码视图可切换 |
| zip | 列出条目与大小；单条目可预览；不整包加载 |

## 6. 待决策

1. **json 要不要压过内置 `code`？**（影响默认体验）
2. **log 的"尾部跟随"是否是必需？**（涉及滚动锚定，成本不低）
3. **yaml 是否值得为它引一个解析器？**（当前建议：不做语义解析）
4. **zip 是否进入 P4？**（取决于你是否真的会在侧边栏翻压缩包）
